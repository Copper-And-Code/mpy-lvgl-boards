    Waveshare RP2350-Touch-LCD-4: performance and memory¶

    Measured on the board (RP2350B, 16 MB flash, no PSRAM: U9 not fitted), MicroPython v1.29.0, MICROPY_HW_RGBPANEL_SCALE = 2 (240x240 framebuffer shown as 2x2 pixels). LVGL 9.5 through PyDevices omnipython-lvgl (c34fbee since 2026-11-10, 665dec5 since 2026-11-11: the same numbers, 46 KB less flash, see the end of the next section) with its memory pools (next section); the sections after it were measured before, on lvgl-micropython 3e287e7 / lvgl-bindings 7740c2f, the same LVGL. Raw logs in docs/log/.

    omnipython-lvgl and LVGL's memory pools (2026-11-10)¶

    The board moved from the archived lvgl-micropython to omnipython-lvgl c34fbee, like the other boards, with LVGL's memory pools on (LVMP_POOL_TLSF in mpconfigboard.h; the binding's TLSF pools, held in GC blocks, from 32 KB doubling up to 256 KB). Measured on board 2, whose GT911 does not answer (log/board2-check.txt), so without touch, log/rp2350-opl-c34fbee.txt:

    • Same image: the 64 tile CRCs of t04_crc.py match the earlier ones (and the unix port).
    • Same speed on a clean heap: t06_perf.py 16.6 ms at 150 MHz, 13.1 ms at 200 and 240 MHz (two buffers, so frame-bound), 57.67 / 76.67 fps, no underruns.
    • t02_lvgl_smoke.py across soft resets, t03_panel.py (57.80 fps, 0 underruns, flash writes included), t07_lvgl_oom.py as before (the half-done refresh after a MemoryError is still there, docs/upstream/pydevices-issue-oom-render.md).
    • 26 KB less free heap: 190 KB after import display_driver instead of 215 KB.
    • 1 h soak (t06_soak.py, two buffers): 57.73 fps, 0 underruns, 0 errors, lowest free heap 151 KB (84 KB before), 668 800 Python allocations (374 400 before, in the same hour) (log/rp2350-soak-opl.txt).
    • The 10 examples start and keep running, 151-189 KB free, 0 underruns; not played, no touch on this board (log/rp2350-examples-opl.txt).
    • Board 1 (with touch), the same file: the same figures (CRCs, perf, heap states), LVGL clicks 3/3, the 5 touch targets at the corners and centre, GT911 read() 200 us (236 before), the 10 examples start, Breakout played by hand: touch responsive, no glitches (log/rp2350-board1-opl.txt).

    The pools fix the open issue below. lv.refr_now() of scene_static after a 60 ms pause, median of 15, the same firmware built with and without the pools (LVMP_POOLS=none), log/rp2350-heap-states-opl.txt:

    heap two buffers, no pools two buffers, pools one buffer, no pools one buffer, pools
    clean 26.5 ms 26.5 ms 10.5 ms 9.6 ms
    30 KB of garbage 26.0 ms 26.5 ms 9.3 ms 9.6 ms
    60 KB of small live objects 43.2 ms 26.5 ms 9.3 ms 9.6 ms
    small live objects with holes 43.8 ms 26.5 ms 17.0 ms 9.6 ms

    With the pools every heap state costs the same. Without them the extra time appears in the same kind of heap states as in the table of 2026-11-05 below: so it was LVGL's allocations walking the GC heap (gc_alloc() starts from the first free block), as on the STM32H7_CORE (docs/stm32h743.md). The two-buffer figures include the wait for the end of the frame.

    The pool layout script of the STM32 boards (24 buttons and 6 sliders, a 2 KB block per hole, 80 KB, log/rp2350-pool-layouts-opl.txt) shows the same with two buffers (refresh 51.8 ms in every layout with the pools, 34.5 ms fresh and 68.9 ms fragmented without); with one buffer its scene renders in 35.2 ms with the pools, 33.6-33.9 ms without, so here the pools cost 1.6 ms when the heap is not in the way. gc.collect(): 2.3-5.2 ms with the pools, 2.0-5.0 ms without.

    omnipython-lvgl 665dec5 (2026-11-11, board 1, log/opl-665dec5-all-boards.txt): its PR #19 makes an LVGL assert pass only the file's base name and the line, 46,336 B less flash. Same 64 tile CRCs, the same t06_perf.py figures (57.67 / 76.67 fps, 13.1 ms at 200 MHz), the same 350 KB free after boot, and display.set_tile_cnt(256) raises RuntimeError: LVGL assert failed at lv_display.c:614 with LVGL still running.

    Scan-out and rendering vs clock¶

    Core voltage untouched (default 1.10 V). machine.freq() then rgbpanel.init(pclk_hz=...). refr_now = full-screen invalidated lv.refr_now() of tests/hil/scene_static.py, single buffer (no wait for the buffer swap). Source: log/phase6-perf.txt.

    sys clock PCLK divider fps measured (nominal) refr_now avg underruns (3 s / 200 KB flash write)
    150 MHz 15 MHz 5 57.67 (57.73) 9.23 ms 0 / 0
    200 MHz 20 MHz 5 76.67 (76.97) 7.86 ms 0 / 0
    240 MHz 20 MHz 6 76.67 (76.97) 7.25 ms 0 / 0

    Rendering speeds up less than the clock (150 → 240 MHz = x1.6, refr_now x1.27): code runs from QSPI flash (XIP), whose clock divider MicroPython raises with the system clock.

    Long flash-write test at 150 MHz: 107 x 200 KB in 90 s, 5219 frames (57.73 fps), 0 underruns, no visible glitch (log/phase3-flash-stress.txt).

    Tearing and double buffering¶

    With one framebuffer LVGL (DIRECT mode) draws into the buffer being scanned out: a vertical bar sweeping across the screen showed visibly broken/offset (Nunzio, by eye). Waiting for VSYNC in the flush callback cannot help in that mode (the drawing is already done when flush is called).

    Fix: double buffering at 240x240, which fits in SRAM (a second 480x480 buffer would not). rgbpanel.init(buffers=2) allocates a second framebuffer and its list of control blocks on the GC heap (122 896 B). The DMA block that ends every frame reads the list for the next frame from a variable: pointing it at the other list swaps buffers exactly at the end of a frame, in hardware, with no ISR. swap() returns once the control DMA channel reads from the new list (so the old buffer is no longer read). LVGL draws into the hidden buffer; the flush callback (in C) swaps. Result: bar straight, movement smooth (by eye).

    display_driver uses two buffers by default (falls back to one on MemoryError). Full-screen lv.refr_now() then takes ~17 ms (9.2 ms rendering + wait for the end of the frame): LVGL refreshes at most once per panel frame (57.7 Hz at PCLK 15 MHz). Pixel check vs the unix port still 64/64 tiles identical (log/phase6-crc-doublebuf.txt).

    Was open: a full redraw sometimes costs one frame more with two buffers¶

    Solved by LVGL's memory pools: see above. The analysis as it was on 2026-11-05:

    tests/hil/t06_perf.py no longer reproduces the table above: display_driver now uses two buffers, so refr_now includes the wait for the swap and reads the frame, not the rendering (17.2 ms at 57.7 Hz, 12.9 ms at 77 Hz). Back to back, or from a pause that ends early enough, it can read two frames (26 and 34 ms). This is no regression: the published firmware and the omnipython-lvgl build give the same figures.

    Measured on the 240x240 scene (2026-11-05, 150 MHz), lv.refr_now() after a pause:

    heap one buffer two buffers
    clean 9.5 ms 11.5 ms
    30 KB of garbage 8.9 ms 28.8 ms
    60 KB of small live objects 8.9 ms 28.8 ms
    small live objects with holes 14.7 ms 28.8 ms

    Timed inside the flush: the wait for the swap stays short (3 ms); LVGL reaches the flush at 9.4 ms in the first case and 24.7 ms in the slow one. So the extra 15 ms are in LVGL, before the flush, and only with two buffers.

    Ruled out, by measurement: free memory (slow with over 200 KB free), gc.collect() as a remedy, the flash clock (QMI M0_TIMING unchanged), the XIP cache (same misses), flash writes as such, one extra refresh (one REFR_START per refr_now), and the second framebuffer being in the GC heap (a static one gives the same figures, and loses 120 KB with one buffer).

    Not known: where the 15 ms go, and why they depend on the heap. They look like a copy of the 115 KB between the buffers, but refr_sync_areas() should have nothing to copy with the whole screen invalidated. Python event callbacks on the display made the slowdown disappear for the same garbage, probably by changing the heap, so timing from Python does not settle it: the next step is timing inside LVGL, in C, with nothing that allocates.

    Effect: full-screen redraws at about 34 per second instead of 57 in those heap states; the image stays correct. Small redraws were not measured in those states.

    Robustness: Ctrl-C and soft reset¶

    • Flush callback in C (rgbpanel.lv_display_create()): with a Python flush_cb, a KeyboardInterrupt (Ctrl-C, or the Ctrl-C mpremote sends before every command) landing inside it is printed and swallowed by the binding, flush_ready() is never called, and LVGL's next refresh waits for the flush forever: the board hung (USB up, REPL dead, power cycle needed). With the Python flush + double buffer the board hung in 2 of 3 soft-reset sequences (the third passed by timing luck); with the C flush 6/6 soft resets with LVGL live were clean (log/phase6-softreset-debug.txt).
    • Ctrl-C reaches the program: lv.timer_handler() takes most of the CPU, so a KeyboardInterrupt usually lands in display_driver's callbacks; there it now stops the timer, and the next Ctrl-C reaches the program (mpremote sends several). 3/3 interrupts of a running LVGL program succeeded at the first mpremote attempt (log/phase6-ctrlc.txt). display_driver.start() resumes.
    • Soft reset: the board hook moves the image to the static framebuffer if the GC one was shown, drops the GC buffer, and clears LVGL's root (binding bug, see upstream/pydevices-issue-soft-reset.md). Scan-out keeps running throughout.

    Soak tests (150 MHz)¶

    Configuration Duration Frames fps Underruns Errors Python allocations GC free, per-minute samples (t ≥ 60 s)
    single buffer, Python flush 3600 s 207 823 57.73 0 0 668 760 252 848 .. 270 912 B
    double buffer, C flush 3600 s 207 828 57.73 0 0 374 400 66 688 .. 147 952 B

    Scene: sweeping bar animation, spinner, label updated 5x/s, list/string churn, gc.collect() every 10 s (tests/hil/t06_soak.py, log/phase6-soak.txt, log/phase6-soak-doublebuf.txt).

    • No leak: GC free has no trend over the hour in either run. The samples are taken between collections, so they include garbage; the single 66 688 B sample in the double buffer run is one such instant (the next minute is back at 139 840 B).
    • The min_free column printed by the test is not meaningful: its starting value is gc.mem_free() before the first gc.collect() and no later sample went below it.
    • The Python loop ran ~44 % fewer iterations with double buffering (allocation count): most likely because the flush busy-waits for the end of the panel frame on every refresh, which leaves less CPU to the main loop at 150 MHz.

    Changing machine.freq()¶

    The scan-out runs from clk_sys: after machine.freq(f) the PCLK scales with it until rgbpanel.init(pclk_hz=...) is called. init() notices the new system clock and restarts the scan-out with the new divider (panel not re-initialised, framebuffer kept, the shown buffer kept). Only integer dividers are accepted: e.g. 200 MHz with 15 MHz PCLK is refused with ValueError (no fractional-divider jitter). Decision: the driver does not follow clock changes by itself (MicroPython has no hook for that); applications call rgbpanel.init() after machine.freq(). The GT911 (I2C1, 400 kHz) answers normally at 240 MHz and back at 150 MHz without re-initialisation (log/phase6-touch-freq.txt).

    Region Bytes Notes

    .bss total 135 900
    — rgbpanel_fb (240x240 RGB565) 115 200 static, scanned out by DMA
    — rgbpanel_cb (481 control blocks) 7 696
    — mp_state_ctx 9 076
    — rest 3 928
    C heap (.heap) 2 048
    MicroPython GC heap 365 476 __GcHeapStart 0x20025c5c .. __GcHeapEnd 0x2007f000
    core 1 stack 4 096 0x2007f000 .. 0x20080000
    core 0 stack (SCRATCH_X/Y) 8 192 0x20080000 .. 0x20082000

    GC heap free (gc.mem_free()): 345 056 B with rgbpanel only; 331 968 B right after import display_driver; ~274 000 B with a small LVGL scene and touch.

    With a second framebuffer for double buffering (init(buffers=2), GC heap): 115 200 + 7 696 B more: gc.mem_free() ~211 000 B right after import display_driver with two buffers and touch.

    480x480 is not possible without PSRAM: a 460 800 B framebuffer leaves ~27 KiB of SRAM heap for everything else. With PSRAM the GC heap moves to PSRAM and the framebuffer takes the SRAM heap area instead (next section).

    PSRAM (2026-11-20)¶

    Board 1 with an 8 MB PSRAM (APS6404L) fitted on U9 by the owner. Full log: log/rp2350-psram-probe-2026-11-20.txt, soak log/rp2350-psram480-soak-2026-11-20.txt.

    The memory. Detected at boot on CS GPIO47 by v0.1.7 as is: GC heap 8 553 280 B. 8 patterns over 8 192 000 B, 0 errors, at the QMI's 75 MHz (150 MHz system clock) and at 120 MHz (240 MHz). The Ctrl-C contract (4 x 60) passed with the heap in PSRAM, 28.3 fps as before.

    Bandwidth. DMA read of one 480x480 frame: 26.7 / 28.1 MB/s (cached / uncached alias) at 150 MHz, 42.8 / 45.6 MB/s at 240 MHz, the same with the CPU reading or writing PSRAM. A 480x480 scan-out needs 26.6 MB/s on average, 30 MB/s within a line at PCLK 15 MHz.

    Why the framebuffer cannot be in PSRAM. Bandwidth is not the problem; the PIO FIFO holds 16 pixels (1.1 us at 15 MHz) and any DMA access to XIP holds the DMA engine up for 2-4 us, also for channels that only read SRAM. Measured on v0.1.7 (240x240 from SRAM), underruns in 20 s while a second DMA channel copies in a loop:

    Second channel Underruns
    none 0
    PSRAM to SRAM 401 (every poll)
    SRAM to SRAM 0
    XIP stream FIFO (PSRAM, paced by DREQ_XIP_STREAM) 399

    With the PSRAM copy running, the scan-out is clean from PCLK 7.5 MHz on (x2: the FIFO covers 4.3 us), not at 15 MHz (2.1 us); a 480x480 scan-out would need ~3.75 MHz (14 Hz). The CPU reading PSRAM does not disturb the DMA (0 underruns).

    Tried and dropped: - Framebuffer in PSRAM, read by the panel DMA: the PIO stalls and stays late (the line-start IRQ is already pending), the picture shifts right with stray pixels. - An 8-line ring in SRAM filled by two more DMA channels from PSRAM: the same stalls, through the shared DMA engine. - Core 1 copying lines into the ring: clean when idle (38.5 Hz at PCLK 10 MHz; one core copies ~20 MB/s at 240 MHz), but core 0 writing PSRAM (LVGL drawing) starves it: 94 % of the lines late, i.e. shown 8 lines off.

    What the firmware does (modules/rgbpanel, patches/micropython): at boot, before gc_init(), the board hook MICROPY_BOARD_SRAM_HEAP takes the framebuffer from the end of the SRAM heap area: 480x480 with PSRAM (the GC heap is then PSRAM only), 240x240 without. With PSRAM the system clock goes to 240 MHz before the flash and PSRAM timing is set. Measured (docs/log/rp2350-psram-probe-2026-11-20.txt): - 57.70 fps at PCLK 15 MHz, 0 underruns, also with core 0 writing or reading 1 MB of PSRAM; - t03_panel.py: 57.80 fps, 0 underruns, 0 during 200 KB of flash writes; - Ctrl-C contract 60/60 in all four cases (sleep, stdin, cb, touch), LVGL 28.7 fps with one buffer (log/ctrlc-contract-RP2350-psram480-*.txt); - touch at 1:1: five targets (corners, centre) all hit; - GC heap 8 215 616 B, 8.2 MB free; - soak (t06_soak.py, one buffer, stopped at 30 min instead of 1 h): 57.74 fps, 0 underruns, 0 errors, 240 640 Python allocations, lowest free heap 8 132 576 B, steady at ~8.14 MB (log/rp2350-psram480-soak-2026-11-20.txt).

    One buffer only: a second 480x480 buffer would be on the GC heap in PSRAM, which the panel DMA must not read, so init(buffers=2) raises MemoryError. Applications must also keep rp2.DMA off PSRAM and flash addresses while the panel runs, at either scale.
