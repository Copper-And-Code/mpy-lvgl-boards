# ESP32-4848S040: notes and measurements

ESP32-S3 (240 MHz), 16 MB QIO flash, 8 MB octal PSRAM, 4" 480x480 ST7701 panel on a 16-bit
RGB bus, GT911 touch, CH340 on UART0. MicroPython 1.29, LVGL 9.5. This is the first board
of the repo on [omnipython-lvgl](https://github.com/PyDevices/omnipython-lvgl), the
successor of the archived lvgl-micropython; the others still use that one.

## Build and bench

- `scripts/build.sh esp32 ESP32_4848S040`, which hands over to `scripts/build_esp32.sh`:
  pins MicroPython, omnipython-lvgl (official, not a fork) and ESP-IDF v5.5.2. MicroPython
  1.29 supports the 5.x series only, not ESP-IDF 6.
- Flash, at offset 0 (the image is complete):
  `esptool.py --chip esp32s3 -p /dev/ttyUSB0 -b 460800 write_flash 0x0 dist/<file>.bin`.
  On a board that had other firmware run `esptool.py --chip esp32s3 -p /dev/ttyUSB0 erase_flash`
  first, which erases everything: without it the board can stop at boot with "The filesystem
  appears to be corrupted".
- Run tests through the CH340: `scripts/uart_run.py <test> --dtr 0 --boot-wait 5`. DTR high
  would hold IO0 low. No native USB (see below).
- After changing `sdkconfig.board` or `manifest.py`, delete
  `.work/esp32/micropython/ports/esp32/build-ESP32_4848S040`: an existing build keeps its
  old `sdkconfig`, and a failed build its old `frozen_content.c`, with no warning.
- A global pip index that does not answer makes every ESP-IDF pip install crawl: the
  script sets `PIP_CONFIG_FILE=/dev/null` unless told otherwise.

## What this board hides

- **Native USB must be off.** The USB PHY holds GPIO 19 (touch SDA) and 20 (panel G1).
  MicroPython turns it on by default on the S3, and the only symptom is an empty I2C scan:
  the bus has its pull-ups, SCL works, SDA cannot go low. `MICROPY_HW_ENABLE_USBDEV=0`.
- **Red and blue are swapped** against the published pin lists: GPIO 4, 5, 6, 7, 15 are the
  high bits of the pixel, not the low ones. Checked by eye with colour bars and ramps.
- **The panel has no reset line**: it keeps its state across a reset of the ESP32, so a
  change to its init does not show until the next power cycle unless the sequence starts
  with a software reset (`0x01`). It does now.
- **Not inverted.** The source of the init sequence sends `0x21`; here that shows the
  negative, so the sequence ends with `0x20`.
- GT911 RST and INT are not wired; `gt911.GT911(rst=None)`. Coordinates are panel pixels,
  no rotation or mirroring (5 targets hit, 1-18 px off = finger size). `read()` 227 us.
  The page we took the pins from says SCL is 20 in the text, 45 in its JSON: it is 45.

## Display driver (`modules/esp_rgb`)

Same interface as `st_ltdc` and `rgbpanel`, on ESP-IDF's `esp_lcd`. Two framebuffers in
PSRAM, outside the GC heap, so the image survives a soft reset. Two bounce buffers of 20
lines in internal RAM, filled by the CPU in an interrupt: the LCD DMA reading PSRAM directly
loses pixels when anything else uses that memory. That interrupt copies 24 MB/s and stays on
the core that creates the panel, so `esp_rgb.init()` creates it from a task on the other
core: MicroPython keeps its core (loop speed 137 000 -> 145 000/s of 147 000). `CONFIG_LCD_RGB_ISR_IRAM_SAFE` and
`CONFIG_SPIRAM_XIP_FROM_PSRAM` keep the panel running during flash writes: code and
constants run from PSRAM (which is why the heap is 5.7 MB, not 8).

`esp_lcd` does not report FIFO underruns, so unlike the other drivers there is no counter:
lost pixels only show on the panel.

**Soft reset**: this port has no board hook after a soft reset, where the other drivers call
`mp_lv_deinit_gc()`, and a later `lv.init()` panics (LoadProhibited). The board's `_boot.py`
calls `esp_rgb.lvgl_guard()`, which leaves an object whose finaliser does it, run by
`gc_sweep_all()`. So no patch to MicroPython. Because a board can freeze only one
`_boot.py`, `manifest.py` lists the port's modules one by one.

## Measured

| | |
|---|---|
| Panel | 42.20 fps (nominal 42.27 at 12 MHz), the same during 200 KB of flash writes |
| Full refresh, 48 buttons | 88 ms after a pause, 94-97 ms back to back |
| Small label change | 2.9 ms after a pause |
| `gc.collect()` with 2 MB of data | 120 ms |
| Soft resets with LVGL left initialised | 3/3 |
| WiFi | see below |

Soak of 15 minutes (`tests/hil/esp32/t05_soak.py`: a full-height bar, a spinner, a label,
Python allocations, 2 MB of application data, `gc.collect()` every 10 s): LVGL 39.1
refreshes/s, panel 42.28 fps, 0 errors, 0 touch errors, memory flat (2.55-2.57 MB free). Log:
`docs/log/esp32-phase5-soak-4848S040.txt`. `gc.collect()` still stops the animation for 120 ms,
about 5 frames.

**Where the speed came from.** Full refresh, step by step:

| | |
|---|---|
| panel interrupt on the same core, 16 KB/32 KB caches | 145 ms |
| interrupt on the other core | 133 ms |
| instruction cache 32 KB, data cache 64 KB, 64-byte lines | 88 ms |

Everything LVGL touches is behind the cache: code and constants (XIP from PSRAM), the heap
and the framebuffers. The caches cost 16 KB of internal RAM. The firmware was already `-O2`.

**Tried and dropped**: PARTIAL mode with render buffers in internal RAM (strips copied to the
hidden framebuffer, then to the other one). Worse with any height: 112-114 ms at 100 lines
against 88, 290 ms at 20 before the caches: each strip walks all the objects again, and the
copies add up. Rendering into PSRAM was not the limit.

The pools of `lv_mem_core_micropython.c` are off on this board, as on any stock ESP32 build
(see `docs/upstream/pydevices-pr-lvmp-pools-tlsf.md`).

## WiFi

`network` and `socket` work as shipped. `tests/hil/esp32/t06_wifi.py`, with LVGL animating
(RSSI read once, after connecting; it moved between -47 and -82 with nothing touched):

| | |
|---|---|
| Connect | 3.9-5.3 s; reconnect 3.9 s |
| HTTP request to the internet, DNS included | 91-211 ms |
| Connected, no traffic | LVGL 39-46 refreshes/s, longest gap 36-59 ms |
| Largest internal RAM block | 128 KB before, 80-88 KB after, not given back by `active(False)` |
| Panel | 42.2-42.3 fps in every phase |

TCP download for 10 s, the board reading 4 KB at a time. The first table is the periodic timer
of v0.1.2, the second the one-shot timer (see below), 18 downloads in three runs, alternating:

| RSSI | LVGL | Longest gap | Speed |
|---|---|---|---|
| -48 | 45.0/s | 163 ms | 6.07 Mbit/s |
| -82 | 29.8/s | 908 ms | 3.66 Mbit/s |
| -45 | 21.6/s | 1015 ms | 2.72 Mbit/s |
| -67 | 11.0/s | 912 ms | 0.95 Mbit/s |

| Read | LVGL | Longest gap | Speed |
|---|---|---|---|
| blocking, `settimeout(5)` | 12.8-47.7/s | 113-215 ms | 0.35-5.2 Mbit/s |
| non-blocking, `sleep_ms(1)` when empty | 50.5-54.1/s | 106-206 ms | 0.36-5.7 Mbit/s |

Read sockets non-blocking in an application with a UI: a blocking read can wait up to 100 ms
in `lwip_recvfrom` (`SOCKET_POLL_US` in `modsocket.c`) without running the scheduler. The gaps
of 100-200 ms that remain are not explained, and neither is the speed, which changes from one
download to the next with the same reading mode. HTTPS not tried.

## The schedule queue

MicroPython's schedule queue has 8 places, and a `time.sleep_ms()` drains it slowly: with a
periodic 5 ms timer that schedules a second callback, as `display_driver` had, a 2 s sleep ran
205 ticks instead of 400. The queue stays full, and whatever else asks for a place is
dropped with no error. That was the cause of two problems:

- the I2S callback of `audio.py` was lost, and the sound never ended (20 sounds in 24 during
  long sleeps, none with polling or with the timer stopped);
- LVGL ran below its rate while sleeping, and the gaps during downloads reached 1 s.

`display_driver` now uses a one-shot timer, armed again at the end of each `lv.timer_handler()`,
so it holds at most one place. 0 lost callbacks in 72 sounds; `t05_perf.py` animation from 47 to
55 refreshes/s; soak of 15 minutes 47.6 refreshes/s against 39.1, 42.28 fps, 0 errors, 0 touch
errors, memory flat (`docs/log/esp32-soak-oneshot-timer-4848S040.txt`).

Note: `repr()` of a `machine.Timer` on the ESP32 prints the two modes swapped.

## Sound

Speaker connector, through an NS4168 on I2S: BCLK GPIO 1, LRCLK GPIO 2, DIN GPIO 40 (pins from
a schematic extract on the Home Assistant community, confirmed by ear). These are also the
**relay pins**: `audio.py` and `buzzer.py` must not be used on a board with the relays fitted.

`audio.py` plays beeps, tones and WAV files (PCM, 16 bit, mono or stereo) in the background;
`buzzer.py` goes through it, so the games have sound with no changes. With the bar animating,
calls return in 2-12 ms and LVGL keeps its rate, longest gap 25 ms.

- A sound comes out about 150 ms after the call, the time to cross the buffers.
- The I2S must keep running until the buffers have played. With one block of silence after
  the sound, a 60 ms beep was never heard; with two, it is.
- The amplifier plays one channel: a stereo file loses the other one.

## State

All 10 examples start without exceptions; Breakout played by hand. Backlight is on/off for
now (GPIO 38). Not done: the relays (GPIO 40, 2, 1), the SD card.
