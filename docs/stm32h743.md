# STM32H743 boards: design notes and measurements

DEV190806042, FK743M5-XIH6, STM32H7_CORE V1.0 / V1.3 on MicroPython 1.29.0 with the
PyDevices LVGL binding (LVGL 9.5). The old port and its sources are described in
`docs/stm32-inventory.md`. Work in progress: filled in phase by phase.

## Build

- Out-of-tree boards in `boards/stm32/<BOARD>/` (`BOARD_DIR`), STM32H7_CORE with
  `BOARD_VARIANT=V10|V13` (required). `scripts/build.sh stm32 <BOARD> [VARIANT]`.
- `manifest.py`: LVGL (`$(LVMP_DIR)/manifest.py`) and `modules/st_ltdc`;
  `manifest_nolvgl.py`: `modules/st_ltdc` only (bring-up). With
  `FROZEN_MANIFEST=.../manifest_nolvgl.py` the build goes to `build-<NAME>-nolvgl` and
  `dist/<NAME>-nolvgl-*`.
- **Floats:** Python floats stay `double` (`MICROPY_FLOAT_IMPL = double`, as in the old
  port; the H743 FPU is double precision). The port then links only MicroPython's
  double libm, while LVGL 9.5 calls `sinf`, `cosf`, `atan2f`, `sqrtf`
  (`lv_arclabel.c`, `lv_indev_gesture.c`): undefined at link time. Fixed on the
  board side, no patch: `boards/stm32/lvgl_libm.mk` adds the single-precision files
  of `lib/libm` that provide them.
- **Soft reset:** `MICROPY_BOARD_END_SOFT_RESET` = `st_ltdc_board_end_soft_reset()`
  (`modules/st_ltdc/st_ltdc.c`): `mp_lv_deinit_gc()` when LVGL is built in, then the
  port's own `boardctrl_end_soft_reset()`. Test: `tests/hil/stm32/t02_lvgl_softreset.py`.
- **Size:** about 1.12 MB of the 2 MB internal flash, 945–953 KiB free (table in
  `docs/stm32-inventory.md`).

## Display driver (`modules/st_ltdc`)

API (module `st_ltdc`, aligned with `rgbpanel` of the RP2350): `init(width, height,
hsync, hbp, hfp, vsync, vbp, vfp, *, polarity=0, pclk_hz=50_000_000, buffers=2,
backlight=100)`, `deinit()`, `framebuffer(i=0)`, `shown()`, `swap(timeout_ms=100)`,
`backlight([pct])`, `frame_count()`, `underruns()`, `wait_vsync(timeout_ms=100)`,
`info()`, and with LVGL `lv_display_create(partial_lines=0)`, `lv_tick_install()`.
Panel timings: `python/panels.py` (`st_ltdc.init(**panels.get("IPS1024x600"))`).

Choices:

- **Framebuffers outside the GC heap** (option b of the plan): the top
  `MICROPY_HW_LTDC_FB_BYTES` = 4 MB of the SDRAM (0xC1C00000-0xC1FFFFFF), the heap
  ends below it (`MICROPY_HEAP_END`, 28 MB of heap). Room for two 1024x600 RGB565
  buffers (2 x 1 228 800 B) and the PARTIAL render buffers. Never freed: the LTDC
  keeps scanning valid memory across a soft reset and the image stays (as on the
  RP2350); no root pointers, nothing to rescue in the soft-reset hook. The old driver
  used `m_malloc` on the heap, which a soft reset frees while the LTDC still reads it.
- **Write-through MPU region on exactly that zone, region 15.** Not region 6 as in the
  old driver: since 1.29 `dma.c` (`dma_protect_rx_region`, SD card reads) reprograms
  and then *disables* regions 6 and 7, which would silently turn the framebuffers back
  to write-back after the first SD read. The zone is 4 MB aligned, as the MPU needs.
- **Registers programmed directly** (LTDC, DMA2D; PLL3 through
  `HAL_RCCEx_PeriphCLKConfig`): no HAL LTDC/DMA2D sources, no `hal_conf` changes, no
  `HAL_LTDC_MspInit` per board. Pins are data in each `mpconfigboard.h`
  (`MICROPY_HW_LTDC_PINS`), checked against `boards/stm32h743_af.csv` and against the
  other pins of each board.
- **Pixel clock at run time**: PLL3 M=5 (5 MHz reference), N and R searched for the
  closest output, VCO 192-836 MHz. 50 MHz gives N=40, R=4, the old fixed setting.
- **Swap without an ISR doing LVGL work**: the flush writes the new layer address and
  asks for a reload at vertical blanking, and returns with the flush pending; LVGL's
  `flush_wait_cb` polls until the LTDC has taken it (at most one frame), which LVGL
  calls only before it touches the buffer that was on screen, at the start of the next
  refresh. Phase 5: before, the flush itself waited (up to 17 ms per refresh). The
  only interrupt handler counts frames (line interrupt after the active area), FIFO
  underruns and transfer errors. On the H7 these are **two vectors**: `LTDC_IRQn`
  (line) and `LTDC_ER_IRQn` (underrun, transfer error); the first build enabled only
  the first, so underruns could not be counted (found on hardware, fixed). Priority 5,
  above `IRQ_PRI_FLASH` (6): `spibdev.c` raises BASEPRI to it for a whole QSPI
  erase/program, and at `IRQ_PRI_TIMX` (13) the frame counter dropped to 19 fps during
  writes (`docs/log/stm32-phase3-flash-stress-V13-before-fix.txt`); now 58.3.
- **PARTIAL mode**: render buffers in the zone (write-through, so the DMA2D reads what
  the CPU wrote), each area copied by the DMA2D into the shown buffer, synchronously.
- **AXI QoS** as in the old driver (SDRAM target 1 outstanding transaction, LTDC and
  DMA2D before the CPU). Measured in phase 5: no effect either way (CPU benchmarks,
  LVGL refresh times and underruns are the same with the registers at reset values);
  kept as it was.
- **Backlight**: GPIO on/off (`MICROPY_HW_LTDC_BL`, active high as in the old driver,
  `MICROPY_HW_LTDC_BL_ACTIVE`); PWM after the polarity is confirmed by eye.
- **RGB565 only** (LVGL's colour depth in the PyDevices `lv_conf.h` is 16).

Tests: `tests/hil/stm32/t03_panel.py` (patterns A-D, frame rate, underruns, flash
write), `tests/hil/stm32/flash_stress.py`, `tests/hil/stm32/t03_softreset.py`. The
Python side of the first two was run on the unix port with a stand-in `st_ltdc`
(pattern pixels checked: corners, bar colours, 32/64 ramp steps), then on hardware
(below).

## Touch and `display_driver` (phase 4)

- `python/stm32_board.py` (frozen): touch wiring per board, picked from
  `os.uname().machine`; `stm32_board.touch()` returns a `gt911.GT911` (the same
  `python/gt911.py` as the RP2350, pins given by name) on SoftI2C or hardware I2C at
  400 kHz; `stm32_board.panel()` reads `PANEL` from `/flash/display_config.py`.
- `python/stm32/display_driver.py` (frozen as `display_driver`, LVGL builds only): same
  interface as the RP2350 one (`import display_driver`; `disp`, `touch`, `indev`,
  `start()`, `stop()`, `WIDTH`, `HEIGHT`): `st_ltdc.init()` with the panel timings, DIRECT
  mode on two framebuffers, `lv.timer_handler()` every 5 ms from a soft `Timer(-1)`.
- GT911 on the V1.3 (IPS1024x600): fw 0x1060, config v130, **1024x600 in its own
  config**, so coordinates are panel pixels (scale 1); address 0x5D; command register
  0xFF after power-on, set to 0 by `GT911()` as on the RP2350.
- Measured on the V1.3: orientation, no rotation or mirroring (5 targets hit, 4-15 px
  off = finger size, `docs/log/stm32-phase4-t04_touch_paint-V13.txt`); `read()` with no
  touch 124 us bare, 229 us with LVGL running; LVGL button 5 taps = 5 clicks, read_cb
  every ~33 ms (LVGL's indev period), max 446 us, 0 underruns
  (`docs/log/stm32-phase4-t04_click-V13.txt`).

## Performance (phase 5)

Measured on the V1.3 with the IPS1024x600 at 58.3 Hz (`tests/hil/stm32/t05_perf.py`,
logs `docs/log/stm32-phase5-*-V13.txt`).

- **SDRAM bandwidth is the limit.** 16-bit bus at 120 MHz: CPU reads about 150 MB/s
  with the LTDC off, about 95 MB/s while it scans out (it takes 1024 x 600 x 2 x 58 =
  71 MB/s); SDRAM to SDRAM copies 45-65 MB/s (CPU or DMA2D); writes from AXI SRAM to
  SDRAM 137-145 MB/s. Bank conflicts with the LTDC cost little (90 against ~100 MB/s).
  The heap's write-back cache is slower for streaming writes than the write-through
  zone (49 against 142 MB/s: write-allocate reads every line first).
- **CPU cost of the LTDC**: Python code +0-1 % (runs from cache); 1 MB copies -34 %,
  `gc.collect()` +20-24 %.
- **LVGL allocations were the real bottleneck.** The binding allocates LVGL memory with
  `gc_alloc()`, which walks the allocation table from the first free block; a multi-block
  allocation does not move that hint. With 2 MB of bytearrays behind a free block, an 8 KB
  allocation cost 611 us instead of 181 and a full refresh of 48 buttons **575 ms
  instead of 54** (the refresh makes about 1200 allocations). Fixed by
  `patches/lvgl-micropython/0001-lvmp-pools-on-lvgl-tlsf.patch`: the binding's ESP32 pools
  (LVGL memory in 256 KB TLSF pools that are GC blocks behind a root pointer, so the GC
  still sees every object LVGL refers to) extended to other ports with LVGL's own TLSF,
  enabled for these boards by `boards/stm32/lvgl_pool.mk` (`LVMP_POOL_TLSF=1`). Now 50-51
  ms in every heap state. Checked: 300 callbacks reachable only through LVGL survive
  garbage and collections, also after `lv.deinit()`/`lv.init()` and soft resets
  (`tests/hil/stm32/t05_lvgl_gc.py`); memory back to the same value after `lv.deinit()`.
- LVGL on the panel, scene of 48 buttons, 2 MB of bytearrays in the heap, after the fix:

  | mode | full refresh | small label change |
  |---|---|---|
  | DIRECT, 2 buffers (display_driver) | 56-66 ms | 17-18 ms (waits for vertical blanking) |
  | DIRECT, 1 buffer | 52 ms | 0.9-1.2 ms (tearing possible) |
  | PARTIAL, 60 lines | 86 ms | 0.9-1.2 ms |
  | PARTIAL, 200 lines | 78 ms | 0.8-1.2 ms |

  Before the fix: 273, 257, 384, 243 ms. 0 underruns in every case.
- **Animation rate** (`tests/hil/stm32/t05_soak.py`: a full-height bar sweeping, a
  spinner, a label, Python allocations, 2 MB of application data): LVGL refreshes per
  second 19.2 with the blocking flush and LVGL's 33 ms refresh period, **34.5** with the
  flush wait moved to `flush_wait_cb` and `display_driver.REFR_PERIOD_MS = 16`. Not 58:
  the 16 ms LVGL timer is not locked to the 17.15 ms frame, and each refresh re-renders
  the spinner and copies the changed areas between the two SDRAM buffers. No tearing
  (bar straight, by eye).
- **GT911 over SoftI2C**: 1 `OSError` (ENODEV) in about 9000 polls (3 in the 15 min
  soak). `gt911.lv_read_cb` now keeps the last state and counts it in `touch.errors`
  instead of raising out of LVGL's input read. Not explained yet; a suspect is SoftI2C's
  clock-stretching timeout (255 us by default).
- Possible next step, not done: PARTIAL render buffers in AXI SRAM (unused when the GC
  heap is in SDRAM). Rendering alone took 33 ms there against 53-59 ms in SDRAM, and
  the DMA2D copies AXI to SDRAM at 137 MB/s against 48 from SDRAM.

## Bench: flashing and running tests over UART1 (STM32H7_CORE V1.3)

The V1.3 on the bench is wired to a CH340 USB-serial adapter on UART1 (PA9/PA10, the
second REPL) with **DTR -> BOOT0 and RTS -> NRST**; native USB is not connected.
Measured line levels: DTR=0 puts BOOT0 high, RTS=1 holds NRST low.

- `scripts/stm32_uart_flash.py flash <fw>.hex --verify`: ST system bootloader over
  the UART (AN3155, v3.1, chip id 0x450), erases only the sectors in the image.
  Full LVGL image: 9 sectors, about 2.5 min at 115200 with verify.
  `machine.bootloader()` from the old 1.27 firmware did not reach USB DFU (it reset
  into MicroPython).
- `scripts/uart_run.py a.py [b.py ...] [--soft-reset]`: raw REPL runner, like
  `mpremote run`. **Linux raises DTR/RTS for a moment at every open of the port, and
  that pulse on RTS hard-resets the board**; mpremote toggles them too. So every call
  starts from a fresh boot, and soft-reset tests must run as several scripts in one
  call. The first runs of t02/t03 soft-reset tests were invalid for this reason
  (`ticks_ms` about 2.7 s, `reset_cause` 2) and were repeated in one session.
